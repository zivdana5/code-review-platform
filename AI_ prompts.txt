Save the scan request time as a datetime value when you create the scan row.

For your project, this time means:

Best practice: save time in UTC

Use UTC time instead of local Israel time.

Why? Because UTC avoids timezone bugs. Your computer, another reviewer’s computer, or Docker can all have different local settings. UTC is the clean “universal clock” for backend systems.

from datetime import datetime, timezone

created_at = datetime.now(timezone.utc)

This gives you a timezone-aware datetime.

When a new scan is created:

Then save both in the DB:

import json
from typing import Any


class CodeReviewer:
    def __init__(self, llm_client: OllamaClient, rules: list[ReviewRule]):
        self.llm_client = llm_client
        self.rules = rules

    def review_code(self, code: str) -> dict[str, Any]:
        """
        Run all review rules on the given Python code.

        Returns only rule_id and true/false result for each rule.
        """

        final_results = []

        for rule in self.rules:
            prompt = rule.build_prompt(code)

            try:
                model_response_text = self.llm_client.ask(prompt)
                parsed_response = self._parse_model_response(model_response_text)

                rule_result = {
                    "rule_id": rule.rule_id,
                    "passed": parsed_response["passed"],
                }

            except Exception:
                rule_result = {
                    "rule_id": rule.rule_id,
                    "passed": False,
                }

            final_results.append(rule_result)

        return {
            "rules": final_results
        }

    def _parse_model_response(self, response_text: str) -> dict[str, Any]:
        """
        Parse the LLM response as JSON.

        Expected format:
        {
            "passed": true
        }
        """

        try:
            parsed = json.loads(response_text)
        except json.JSONDecodeError:
            raise ValueError("Model response is not valid JSON.")

        if not isinstance(parsed, dict):
            raise ValueError("Model response must be a JSON object.")

        if "passed" not in parsed:
            raise ValueError("Model response is missing 'passed' field.")

        if not isinstance(parsed["passed"], bool):
            raise ValueError("'passed' field must be true or false.")

        return parsed

def get_scan_by_hash(self, code_hash: str) -> Optional[Scan]:
    now = datetime.now(timezone.utc)

    with Session(self.engine) as session:
        statement = (
            select(Scan)
            .where(Scan.code_hash == code_hash)
            .where(Scan.expires_at > now)
            .where(Scan.status != STATUS_FAILED)
            .order_by(Scan.created_at.desc())

Yes. The difference is mainly how you structure the input and what kind of task you are doing.

In your project, both can work, but I recommend /api/chat.

The simple idea
/api/generate

/api/generate is the simpler endpoint.

You send one big prompt:

You are a strict Python code reviewer.
Check this code.
Return only JSON.

Code:
...

So the request looks like:

payload = {
    "model": "qwen2.5-coder:7b",
    "prompt": prompt,
    "stream": False
}

The answer comes back in:

data["response"]
/api/chat

/api/chat is the chat-style endpoint.

Instead of one big prompt, you send a list of messages with roles:

system: You are a strict Python code reviewer.
user: Check this code and return JSON.

So the request looks like:

payload = {
    "model": "qwen2.5-coder:7b",
    "messages": [
        {
            "role": "system",
            "content": "You are a strict Python code reviewer. Return only valid JSON."
        },
        {
            "role": "user",
            "content": prompt
        }
    ],
    "stream": False
}

The answer comes back in:

data["message"]["content"]
Main difference
/api/generate = one raw prompt

You give the model a single block of text.

Example:

Rule:
Check if variable names are meaningful.

Return only:
{"passed": true}
or
{"passed": false}

Code:

    return x + 1

This is simple and perfectly fine.

/api/chat = structured conversation

You separate the “instruction” from the “user task”.

Example:

messages = [
    {
        "role": "system",

    return x + 1

    }

This is cleaner for a real app.

Better for assistant-like behavior	Less	Yes

Change your OllamaClient to this:

class OllamaClient:
    def __init__(
        self,
        base_url: str = OLLAMA_BASE_URL,
        endpoint: str = OLLAMA_ENDPOINT,
        model: str = OLLAMA_MODEL,
        timeout_seconds: int = OLLAMA_TIMEOUT_SECONDS,
        system_prompt: str = DEFAULT_SYSTEM_PROMPT
    ):
        self.base_url = base_url.rstrip("/")
        self.endpoint = endpoint
        self.model = model
        self.timeout_seconds = timeout_seconds
        self.system_prompt = system_prompt

    def ask(self, prompt: str) -> str:
        url = f"{self.base_url}{self.endpoint}"

        payload = {
            "model": self.model,
            "messages": [
                {
                    "role": "system",
                    "content": self.system_prompt,
                },
                {
                    "role": "user",
                    "content": prompt,
                },
            ],
            "stream": False,
        }

        try:
            response = requests.post(
                url,
                json=payload,
                timeout=self.timeout_seconds,
            )
            response.raise_for_status()

            data = response.json()

            if "message" not in data:
                raise RuntimeError("Ollama response did not contain a 'message' field.")

            if "content" not in data["message"]:
                raise RuntimeError("Ollama response message did not contain a 'content' field.")

            return data["message"]["content"]

        except requests.exceptions.ConnectionError:
            raise RuntimeError("Could not connect to model provider. Make sure it is running.")

        except requests.exceptions.Timeout:
            raise RuntimeError("Model provider request timed out.")

        except requests.exceptions.RequestException as error:
            raise RuntimeError(f"Model provider request failed: {error}")

        except ValueError:
            raise RuntimeError("Model provider returned an invalid JSON response.")

def get_scan_by_hash(self, code_hash: str, model_name: str) -> Optional[Scan]:
    now = datetime.now(timezone.utc)

    with Session(self.engine) as session:
        statement = (
            select(Scan)
            .where(Scan.code_hash == code_hash)
            .where(Scan.model_name == model_name)
            .where(Scan.expires_at > now)
            .where(Scan.status != STATUS_FAILED)
            .order_by(Scan.created_at.desc())
        )
        return session.exec(statement).first()

Local Python Code Review Platform
Project Description

This project is a local Python code review platform built with FastAPI.

The system receives a Python file through an API, starts an asynchronous code review scan, and returns a scan_id to the user. The user can later use this scan_id to get the scan status and result.

The code review is done by a local LLM using Ollama. The scan result is saved in a local SQLite database for 24 hours.

The project is designed as a simple proof of concept, with a clean structure that makes it easy to add more review rules in the future.

Main Features
Upload a Python .py file.
Start a code review scan asynchronously.
Return a scan_id immediately.
Get scan status and result using the scan_id.
Use a local Ollama model for code review.
Save scan results in a local SQLite database.
Reuse existing results for the same code when possible.
Limit the system to 5 running scans at the same time.
Expire scan results after 24 hours.
Support simple configuration of the local model provider using environment variables.

Code Review Rules

The current code reviewer checks two rules:

1. Meaningful Variable Names

Checks whether variables in the Python code have clear and descriptive names.

Examples of weak names:

x, y, z, a, b, tmp, data, val, foo, bar

Examples of better names:

total_price, user_count, file_content, scan_result
2. Function Docstrings Match Code Logic

Checks whether function docstrings describe what the function actually does.

If a docstring says the function sorts a list, but the code only filters values, the rule should fail.

Validation Rules

Before starting a scan, the platform validates the uploaded file.

The file must:

Exist.
Have a .py extension.
Not be empty.
Be valid UTF-8 text.

If the file is invalid, the API returns a 400 Bad Request error.

Scan Statuses

A scan can have one of these statuses:

running
completed
failed
running

The scan was created and the code review is still in progress.

completed

The scan finished successfully and the result is available.

failed

The scan failed, usually because the local model provider was unavailable or returned an invalid response.

Scan Caching

The system calculates a SHA-256 hash of the uploaded code.

If the same code was already scanned and the result has not expired, the system reuses the existing scan instead of running the LLM again.

This avoids unnecessary repeated scans for identical code.

5 Running Scans Limit

The system allows up to 5 scans to run at the same time.

If 5 scans are already running and the user submits another new scan, the API returns:

{
  "detail": "Too many scans in progress. Please try again later."
}

This protects the local machine from running too many LLM reviews at once.

24 Hour Result Expiration

Each scan result is valid for 24 hours.

When a scan is created, the database stores:

created_at
expires_at

Expired scans are deleted before new scan operations and before fetching scan results.

This keeps the local database small and prevents old results from being reused forever.

Short Design Decisions
FastAPI

FastAPI was chosen because it is simple, modern, and works well for building API services.

It also provides Swagger UI automatically, which makes the project easy to test.

SQLite

SQLite was chosen because it is local, simple to run, and does not require a separate database server.

This fits the requirement that the project should run locally.

SQLModel

SQLModel was used to define the scan table and interact with SQLite in a structured way.

Ollama

Ollama was used because the assignment requires a local LLM.

The platform sends prompts to the local Ollama server and receives a JSON answer from the model.

Background Tasks

The scan endpoint returns a scan_id immediately and runs the code review in the background.

This prevents long API requests and allows the user to fetch the result later.

Code Hashing

The platform hashes the uploaded code to detect duplicate scans.

This allows the system to reuse recent results for the same code.

Separate Components

The project is split into separate files:

API logic
Database logic
Code review logic
Application startup

This keeps the code easier to read, test, and extend.
